# Технологический стек Rubast

> Статус: предложение для обсуждения, 2026-10-06. Выбор Prism и реализация компилятора на Ruby уже согласованы; решение о `dry-system` пока открыто.

## Рекомендация

Первую версию строим как Ruby gem с фиксированным конвейером. Зависимости этапов передаём через конструкторы в одной точке сборки CLI. `dry-system` можно подключить, когда появятся несколько вариантов парсера/бэкенда, плагины, разные режимы сборки или сложная конфигурация. Его применение ограничим точкой сборки и адаптерами; семантика Ruby, IR и проходы анализа не должны зависеть от контейнера.

```text
bin/rubast (Ruby CLI)
  → Compiler (Ruby, точка сборки)
  → Prism adapter → Normalizer → Analyzer → Rust backend
  → Generated Cargo project + bundled Rust runtime
  → cargo build/run
```

## Предлагаемые технологии

| Область | Выбор для первого среза | Почему |
| --- | --- | --- |
| Язык компилятора | CRuby 3.4, точный patch-релиз закрепить до кода | Совпадение с выбранной семантической целью и воспроизводимые тесты |
| Упаковка | Ruby gem, gemspec и Bundler для разработки | Обычный способ распространять Ruby CLI и фиксировать зависимости |
| Парсер | `prism` через Ruby API, версия закреплена | Именованные поля узлов, позиции, ошибки разбора; Prism остаётся единственным источником AST ([API](https://ruby.github.io/prism/rb/docs/ruby_api_md.html)) |
| Загрузка кода | Явные `require` на старте; `zeitwerk` при росте дерева файлов | На первом срезе не требуется второй механизм регистрации компонентов |
| CLI | `OptionParser` | Достаточно для `emit-rust`, `build`, `run` и справки ([документация](https://docs.ruby-lang.org/en/3.4/OptionParser.html)) |
| IR и диагностики | Собственные классы на `Data.define`; вложенные массивы замораживать отдельно | Именованные поля и сопоставление с образцом; `Data` обеспечивает только поверхностную неизменяемость ([документация](https://docs.ruby-lang.org/en/3.4/Data.html)) |
| Внешние процессы | `Open3` с массивом аргументов; отдельный адаптер Cargo | Можно проверять stdout, stderr и код выхода без shell-интерполяции ([документация](https://docs.ruby-lang.org/en/3.4/Open3.html)) |
| Результат | Сгенерированный Rust-проект + исходники `rubast_runtime` | Выходная программа собирается Cargo и не зависит от установленного Ruby ([Cargo](https://doc.rust-lang.org/cargo/)) |
| Проверка | Minitest для Ruby-этапов; дифференциальные тесты против закреплённого CRuby; `cargo test` для runtime | Разделяет ошибки компилятора, несовпадения поведения и ошибки Rust runtime |

Генерируемый проект должен включать исходники нужной версии `rubast_runtime` или получать их из закреплённого пакета. Зависимость по локальному пути на исходный checkout Rubast удобна для разработки, но непереносима для пользователя.

## Где уместен dry-system

[`dry-system`](https://hanakai.org/learn/dry/dry-system/v1.2) предоставляет контейнер компонентов, автоматическую регистрацию, инъекцию зависимостей, providers и режим для тестовых замен. Это полезно, если Rubast получит несколько бэкендов, режимы компиляции с разными адаптерами или расширения сторонних авторов.

Для текущего конвейера он добавляет соглашения об именах файлов, жизненный цикл контейнера и косвенное разрешение зависимостей при небольшом числе объектов. Моя рекомендация к обсуждению: **пока не добавлять `dry-system` в зависимости**, но передавать Parser, Backend и CargoRunner явно. Когда ручная точка сборки станет неудобной, можно заменить её контейнером без изменения IR и алгоритмов проходов. Если решим использовать `dry-system` сразу, пусть он создаёт только верхнеуровневые сервисы; узлы IR и компиляторские проходы должны оставаться обычными Ruby-объектами.

## Что пока не добавляем

`dry-struct` и `dry-types` не нужны для узлов IR: корректность Ruby-программы проверяет собственный анализатор, а `Data.define` достаточно для хранения уже проверенных форм. `dry-monads` можно рассмотреть при усложнении потоков ошибок; на старте достаточно явного результата компиляции и списка диагностик. `dry-cli` можно пересмотреть, если команд и вложенных опций станет существенно больше.

## Первый критерий пересмотра

После сквозного среза `rubast run example.rb` посмотрим, сколько зависимостей собирает CLI и сколько вариантов реализации реально существует. Если конфигурация уже разрастается, введём `dry-system` только в точке сборки. Если нет, сохраним явные конструкторы.
