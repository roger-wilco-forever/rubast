# Build Rubast around verifiable Ruby semantics

**Rubast is a Ruby-written ahead-of-time compiler for a documented subset of Ruby.** Its first measure of success is whether an accepted program behaves like a pinned CRuby version, not how much syntax can be translated into Rust. Prism parses Ruby source, the Ruby compiler builds an intermediate representation (IR) that captures expression meaning and the supported-language boundary, the backend emits a readable Cargo project, and a small Rust runtime implements Ruby values and operations. Spinel demonstrates a similar whole-program pipeline, but its C output, internal AST, and garbage collector are not ready-made Rust designs. We begin with a differential end-to-end scenario and add classes, blocks, exceptions, and metaprogramming only after defining and testing their semantics. Facts about Spinel and Ruby are linked below; Rubast design choices are identified as proposals.

## Implementation status

The first end-to-end slice now accepts a sequence of `puts` calls over supported values and top-level local assignments. Supported expressions include `nil`, booleans, signed 64-bit integers, UTF-8 string literals, `gets`, safe `chomp` on strings or `nil`, local reads, and string interpolation with one supported expression per embedded section. [`examples/hello_user.rb`](../examples/hello_user.rb) prompts for a name, waits for stdin, and prints `Hello, #{user}!`. The generated program forwards stdin and streams stdout and stderr, so the prompt is visible before input arrives. The current input reader expects valid UTF-8.

Running under CRuby 3.4.5, Rubast parses the file with Prism 1.9.0, validates the subset, emits a Cargo project with a local Rust runtime, builds it, and runs the result in a temporary directory. Cucumber compares stdout, stderr, and exit status with CRuby, including Unicode input and EOF. Unsupported syntax, parse errors, invalid string encodings, and out-of-range integers produce diagnostics with Ruby source locations. `dry-system` assembles the compiler stages.

This remains narrower than the planned MVP below. User classes now support constructors and instance methods with required/optional positional arguments, named rest arguments, keywords, keyword rest, and named literal block parameters. Method bodies support expression sequences and scalar/object instance-variable reads and writes. Classes must be defined before use and cannot reopen existing classes or constants. Methods support local assignment, `puts`, explicit `self.method`, and implicit calls to current-receiver helpers, including later-defined methods in the same class; the last expression value is returned, with `nil` for an empty body or a final `puts`. Arguments are evaluated once in order and method locals do not share top-level local scope. `new` invokes private `initialize` and returns the object regardless of its ordinary result. Unset fields read as `nil`; aliases share field mutations and separate instances have independent state. Empty classes, single inheritance from previously defined user classes, inherited constructors, overriding, and explicit/forwarded `super` are supported. Superclass calls preserve the receiver and fields; lookup starts above the defining class, while ordinary calls use the concrete receiver. Bare `super` forwards current parameter values; `super()` supplies no arguments. The default initializer accepts no arguments and returns `nil`. Built-in/computed superclasses, missing non-initializer super targets, explicit `initialize` calls, recursive calls, compound attribute assignment and user index assignment, top-level `self`, and general dynamic dispatch remain unsupported. Object arguments/results and fields preserve aliases; self references and mutual cycles are supported under arena lifetime. Supported parameter operations are checked against the argument and field types at each call. Unused methods are still checked for unsupported syntax and known invalid operations. See [the supported class scenarios](../features/classes.feature), [method-body scenarios](../features/method_bodies.feature), [object-state scenarios](../features/object_state.feature), and [instance-call scenarios](../features/instance_calls.feature), and [inheritance scenarios](../features/inheritance.feature). Scalar conditions (`if`, `unless`, `elsif`, and modifiers), scalar equality, integer ordering, proven-safe integer arithmetic, and explicit method returns are implemented. `while`/`until`, pre/post-test modifiers, `break`, `next`, plain `begin`, and local/instance compound arithmetic assignment are supported. Loop invariants recheck all local and object-field types with integer widening, direct literal-bound guard refinement, and a 16-pass limit. Unbounded integer growth, fresh user objects in loops, `redo`, `for`, and loop-predicate `break`/`next` remain diagnostics. Arrays, hashes, and mutable strings now have shared storage and a bounded supported API; see the collection contract below. Top-level user methods and general Ruby dispatch remain unsupported. The CLI provides `run` and `emit-rust FILE -o DIR`. Emission saves an independently buildable Cargo project with runtime source, without executing Cargo; output directories must be new or empty. A separate `build` command remains planned. Diagnostics currently carry line and column positions, without byte ranges or a Ruby-to-Rust source map. There is no separate `CompilationContext` yet. These remain target contracts for later stages. The agreed implementation sequence is recorded in [the roadmap](roadmap.md).

**Current flow and numeric contract:** scalar truthiness treats only `nil` and `false` as false. Local bindings start as `nil`; generated local and field reads are captured before later side effects. Analysis snapshots locals and fields of all tracked objects, including nested references and cycles, joins branch states and all method exits, and ignores unreachable writes when determining caller-visible state while still validating their semantics. Conditional object-handle choices and object conditions are rejected. Integer intervals prove that `+`, `-`, `*`, `/`, `%`, and unary signs stay within `i64`; division/modulo check zero at runtime and prove the nonzero result ranges. Integer result overflow receives `E_INTEGER_RANGE`; invalid operand types receive `E_UNSUPPORTED`; zero division raises `ZeroDivisionError`. Rust uses `i128` intermediates and Ruby floor-division/modulo rules. Analysis does not narrow integer ranges from ordinary predicates or retain correlations across values, so conservative joins can reject safe Ruby programs. Structured runtime exceptions are implemented; arbitrary-precision integers remain later work. The frontend carries Prism's default-level warnings into program IR; generated programs print them before execution, matching pinned CRuby at default verbosity. Acceptance execution has a 30-second timeout with process-group cleanup. Loop-guard refinement does not broaden ordinary conditional narrowing. See [loop scenarios](../features/loops.feature), [arithmetic scenarios](../features/arithmetic.feature) and [control-flow scenarios](../features/control_flow.feature).

## A closed program sets an honest compatibility boundary

**Rubast proposal:** input is one Ruby file known in full before compilation; output is a standalone program built by Cargo. The first compatibility target is the semantics of selected Ruby 3.4 constructs within an explicit subset. CRuby 3.4.5 and Prism 1.9.0 are pinned for the current implementation so differential tests and parser updates are reproducible. This does not promise support for arbitrary Ruby programs, arbitrary gems, or definitions added dynamically at runtime.

**Spinel fact:** it passes a program through Prism, its own AST, type analysis, C generation, and a system C compiler. Its analysis tracks definitions and call sites, iteratively refines types, and uses a polymorphic representation when types remain ambiguous. Spinel documents fundamental AOT limits, including `eval`, `method_missing`, and dynamic method creation. Rubast can use its stage boundaries, whole-program analysis, and explicit limitations, while designing memory management for Rust separately. ([Spinel: Architecture](https://github.com/matz/spinel/blob/master/README.md#architecture); [Spinel: What analyze does](https://github.com/matz/spinel/blob/master/README.md#what-analyze-does); [Spinel: Fundamental limits](https://github.com/matz/spinel/blob/master/docs/limitations.md#fundamental-limits-inherent-to-aot))

The boundary must be **semantic**, not a list of AST node names. Ruby treats only `nil` and `false` as false, control expressions return values, and `&&` and `||` return an operand. Replacing these rules with Rust `bool` changes even simple programs. An unqualified Ruby name may be a local variable or a method call; Prism distinguishes those cases. Calls also depend on method lookup and potentially `method_missing`. Any form whose meaning Rubast cannot yet preserve must produce a diagnostic against the Ruby source before Rust generation. ([Ruby: Control expressions](https://ruby-doc.org/3.4.1/syntax/control_expressions_rdoc.html); [Ruby: Operators](https://ruby-doc.org/3.4/syntax/operators_rdoc.html); [Ruby: Calling methods](https://ruby-doc.org/3.4/syntax/calling_methods_rdoc.html); [Prism Ruby API](https://github.com/ruby/prism/blob/main/docs/ruby_api.md))

## IR separates Ruby meaning from Rust representation

**Proposed pipeline:** `bytes → Prism AST → normalized Ruby IR → subset validation and name resolution → semantic IR → Rust source + Rust runtime → Cargo`. The CLI, normalizer, analyzer, and emitter are written in Ruby; Cargo builds the generated project. Prism's Ruby API provides the tree, parse errors, and node locations. Keep source bytes and spans until diagnostics are complete. A parse error (`E_PARSE`) must retain Prism's message and location. Encoding affects names and strings, so the planned MVP accepts UTF-8 and diagnoses other encodings instead of silently converting them. ([Prism repository](https://github.com/ruby/prism); [Prism Ruby API](https://github.com/ruby/prism/blob/main/docs/ruby_api.md); [Prism: Encoding](https://github.com/ruby/prism/blob/main/docs/encoding.md))

The repository boundaries are `bin/rubast` for the CLI, `system/` for the container, `app/` for Ruby compiler services, `lib/rubast/` for IR and data, and `runtime/` for code linked into the output binary. Running the compiler requires Ruby and Prism; building output requires Rust and Cargo. The built program must not require Ruby. This is a Rubast implementation choice.

From the first implementation, `dry-system` assembles source reading, the Prism adapter, normalization, analysis, Rust emission, and Cargo execution. The CLI accesses the container; IR nodes and pass algorithms do not. A future per-compilation context will carry run-specific data. Stage contracts and code placement are detailed in the [technology stack](technology-stack.md). The [development guide](development.md) maps the current owners and verification needed to claim support for a new construct.

The planned normalizer reduces syntax variants to a small set of forms and retains `SourceSpan { file, byte_start, byte_end }` for each expression. Subset validation visits **every** node, rejects unsupported semantics, and builds a table of statically known definitions; it must never return a partially translated program. Semantic IR covers `Literal`, `Local`, `Assign`, `Sequence`, `If`, `Loop`, `Call`, `Return`, and explicit `Truthy` checks. Every expression has a result value, a Ruby span, and either a proven type or `Unknown`. Temporaries preserve argument evaluation order. `&&`, `||`, and branches preserve the value of the operand or expression Ruby selected. `Return`, and later `Break`, `Next`, and `Raise`, are distinct from ordinary values. This is the **Rubast IR contract**, not a property of Prism or Spinel.

The backend receives validated IR only. Its target contract is to produce a reproducible Cargo project (`Cargo.toml`, `src/main.rs`, and generated modules when needed), link a versioned `rubast_runtime`, and support `rubast emit-rust`, `rubast build`, and `rubast run`. Conceptually, generated functions take `&mut Runtime` and return `Result<Value, RubyError>`. Early `return` can use an internal `Flow` type or direct Rust control flow when the IR proves equivalence. Rust compiler errors should map back to Ruby spans through a source map. Cases diagnosed before code generation receive stable codes such as `E_UNSUPPORTED`, `E_DYNAMIC_CALL`, `E_TYPE`, and `E_IMPORT`. Rust source is an inspectable artifact that Cargo can build without relying on unstable `rustc` internals. ([Cargo: Creating a new project](https://doc.rust-lang.org/stable/cargo/guide/creating-a-new-project.html); [Rust Compiler Development Guide](https://rustc-dev-guide.rust-lang.org/rustc-driver/intro.html))

| Stage | Input contract | Output contract | Failure |
| --- | --- | --- | --- |
| Parser | Source bytes and pinned syntax version | Prism AST, locations, diagnostics | `E_PARSE` |
| Normalizer | Valid Prism AST | Small set of forms with `SourceSpan` | `E_UNSUPPORTED` for an unknown form |
| Analyzer | Normalized forms and definition table | Validated semantic IR with evaluation order and types | `E_DYNAMIC_CALL`, `E_TYPE`, `E_IMPORT` |
| Backend | Validated IR only | Rust files and Ruby-to-Rust source map | Internal compiler error if an IR invariant is broken |
| Runtime | Calls from generated Rust | Ruby values, operations, output, and structured errors | `RubyError` rather than an accidental Rust `panic!` |

## Start the runtime with correct values, then specialize

**Proposal for the planned runtime:** a common `Value` type with `Nil`, `Bool`, arbitrary-precision integers, and strings. `Runtime` provides `truthy`, arithmetic, comparison, and a restricted `puts`. This is simpler for accepted programs than immediately assigning static Rust types to every Ruby expression. Ruby integers are not limited to machine `i64` values. The first implementation deliberately limits integers to signed 64-bit values and diagnoses numbers outside that range rather than silently wrapping them. ([Ruby: Literals](https://docs.ruby-lang.org/en/3.1/syntax/literals_rdoc.html); [Spinel: Integer overflow](https://github.com/matz/spinel/blob/master/README.md#integer-overflow))

The original MVP proposal below predates the class slice described above. In that proposal, calls to user methods require a proven closed set of definitions: no redefinition, classes, or dynamic lookup. Operations on proven built-in values go through the runtime; unresolved calls receive `E_DYNAMIC_CALL`. This is narrower than Ruby, where classes can reopen, methods can be redefined, and operators such as `+` are method calls. Once the basic semantics work, Rubast can add general method dispatch, then guarded specialization with a fallback to that general path. RBS may help analysis, but a signature alone does not prevent dynamic class changes. ([Ruby: Modules and classes](https://ruby-doc.org/3.4.1/syntax/modules_and_classes_rdoc.html); [Ruby: Calling methods](https://ruby-doc.org/3.4/syntax/calling_methods_rdoc.html); [RBS repository](https://github.com/ruby/rbs))

**Current object representation:** `Value::Object` carries an index into a per-runtime arena of field maps. Cloning a handle preserves identity; fields contain scalars or object handles. Self references and mutual cycles are valid because fields own indices, not recursively owned objects. All arena entries remain allocated until runtime teardown; no collection or finalizers are provided. Analysis keeps a per-run list of object types and snapshots every object's fields at branch/return boundaries, so changes through nested references or object parameters are visible to aliases. Field reads and call results are captured before later side effects. Built-in `==`/`!=` compare identity and `!` uses truthiness; user-defined operators take precedence, including default `!=` negating an overridden `==`.

**Current dispatch contract:** analysis resolves every executed call using its actual argument types and current field state. Unknown parameter/field lookup is deferred only during unused-method checking; known invalid calls and unsupported syntax still fail. Ordinary calls emit a Rust function per class/method and resolved nested-call signature, sharing functions across scalar types and object identities when the targets agree. Calls with literal blocks inline their validated method bodies. Changed object classes can produce different variants of the same method. Signature traversal excludes mutable type graphs, so cycles do not cause recursive hashing. A per-validation active-method stack rejects direct and indirect recursion at the Ruby call location, including recursion through another object. Methods are registered before body validation so helpers can be declared later in the same class. Implicit user methods shadow built-in `gets` and `puts`. Object joins require the same handle on every path; mixed/different object results, object conditions, printing/interpolation, and object safe navigation remain unsupported. Integer/string equality with an object on the right is rejected because Ruby can delegate to the object; identity comparison and user-defined operators on an object receiver are supported. See [object-reference scenarios](../features/object_references.feature) and [the linked-name example](../examples/linked_names.rb).

**Current collection contract:** arrays and hashes use the existing indexed arena, including nested references and cycles. Analysis tracks at most 10,000 slots and requires exact lengths for indexed reads/writes and append; writes require a single proven integer index. Missing reads return `nil`, positive writes fill gaps, and negative indexes use the length after argument evaluation. Fixed slots can mutate in loops; fresh arrays or growing loop shapes remain rejected. Strings use standard-library `Rc<RefCell<String>>` buffers for shared mutation; copies from `+`, `dup`, and `chomp` are independent. Right-hand bytes are captured before mutation, including self-append. Runtime frozen mutations raise `FrozenError`; analysis still rejects unsupported operations before emission. Built-in call families enter the function specialization signature, so integer and string addition cannot share the wrong emitted body. [Collection scenarios](../features/collections.feature) execute the declared APIs and boundaries; [README.md](../README.md) lists them.

Static symbol names support scalar operations and comparisons. Hash keys initially accept single proven Symbol or Integer values. Runtime hash entries use a standard-library vector to preserve insertion order; replacement retains its position. Analysis stores immutable key-order shapes alongside value slots, joins absent keys as `nil`, and bounds alternative orders at 32 and literal-entry/distinct-key counts at 10,000. Presence checks distinguish missing entries from stored `nil`. Independent `keys`/`values` arrays preserve nested aliases; these allocations remain unsupported in loops, and uncertain order prevents traversal snapshots. String/custom keys, defaults, equality, and block traversal remain rejected. See [hash scenarios](../features/hashes.feature).

**Initial inline iterator contract:** `each`, `times`, and `map` support literal blocks with zero or one positional parameter, block-local declarations, captured assignments, nesting, and instance `self`. A fresh normalization session maps Prism local depths to distinct block names; method scope stays isolated. Analysis specializes each known invocation in order, updating captured state and arena fields. Empty receivers check a detached body and restore its effects; unknown generic receivers summarize changed captures/fields as unknown for later decisions. Array length must stay exact and unchanged; integer counts must be single-valued. Analysis caps total body validations at 1,000, including generic method checks and loop passes. Rust emits each step inline, reads array values just before invocation, and starts fresh block bindings while reusing captured outer bindings. Map allocates independent result storage with aliased mutable elements; iterator count/family and nested dispatch enter the function reuse signature. Existing runtime arena/indexing functions are reused. Extended/implicit parameters, dynamic iteration shapes, fresh object/collection bodies, escaped blocks remain unsupported. Ordinary loops inside blocks keep their own exits, and returns from called helpers still target their own methods. This is stage 11's first checkpoint, not complete closure support. See [iterator scenarios](../features/iterators.feature).

**User-method yield contract:** literal blocks attached to user instance calls reuse depth-aware block normalization and the bounded body validator. Yield arguments run once in callee scope; the block runs in lexical caller scope with the caller's self, helper/super context, and captured bindings. Zero-argument yield supplies nil; a one-parameter block takes the first argument without discarding later argument effects. Captured scope maps enter the existing snapshot/restore/join and loop convergence routines alongside callee locals and arena fields. Ordinary helper calls clear the block context; a yield inside a nested supplied block retains its lexical enclosing method's block. Rust emits distinct inline local bindings and a labeled callee boundary, preserving normal method returns without exiting the caller. Function signatures include inlined block syntax and nested targets, excluding cyclic result-type graphs. Ignored blocks are checked detached. Generic unused-method checking defers a missing block; actual yield without a block raises LocalJumpError. Constructors and named super forwarding follow the stage 13 contract below. Safe block navigation, extended literal-block parameters, and escaped blocks remain rejected; fresh allocations in block bodies and total body validations keep the iterator ceilings. [Yield scenarios](../features/yield.feature) and [invoice batch traversal](../examples/yielding_batch.rb) execute this second checkpoint; the block exit contracts below complete stage 11.

**Block-break contract:** analysis resolves a normalized break to an ordinary loop exit when a lexical loop is active, otherwise to a distinct `BlockExit` with the receiving invocation's per-run target id. Block bodies reset loop context; ordinary called methods clear block context. A break evaluates its value once and records projected receiving-caller locals, the target's capture depth, and shared arena state. Normal completion and break states use existing type joins; incompatible object/scalar or different-handle results remain unsupported. Iterator specialization stops after a body that cannot continue, and Rust labels the whole receiving invocation so nested lexical yields can cross intermediate loops and calls. User-method returns use that same receiving boundary; block exits leave the caller running. Detached/ignored/unreachable checking and speculative loop passes discard exit records. Traversed array lengths are checked on exit paths as well as continuing steps. Zero/one break values work; multiple break values remain unsupported. [Block-break scenarios](../features/block_break.feature) and [first large invoice](../examples/first_large_invoice.rb) exercise checkpoint 11c.

**Block-next contract:** each body validation creates a next context with its own exit id and full block scope. Normalized loop-next nodes retain ordinary loop targets when a lexical loop is active; otherwise next records the evaluated result and snapshot in the current body context. Next and normal completion join types, locals, captured scope maps, and arena fields before the enclosing bindings are updated. Bodies containing next lower to `BlockBody` with a distinct label; existing `BlockExit` emission returns its value to that boundary without leaving the receiver's invocation. Each/times discard it, map retains it, and yield returns it to the method. Active body contexts participate in existing dead-code and loop-trial exit trimming, and ordinary methods clear next context. Labels remain defined even when a next value takes another exit. Traversed lengths and existing allocation/count/object-join limits remain checked. Multiple next values remain diagnostics. [Block-next scenarios](../features/block_next.feature) and [invoice labels](../examples/invoice_labels.rb) execute checkpoint 11d.

**Block-return contract:** normalized `Return` nodes are accepted in literal blocks only with a supported lexical defining method. Analysis gives each active method an exit context containing its local map and capture depth; blocks retain that context with their lexical self/helper/yield context. A yield restores the defining context while validating its body, so intervening callees cannot collect its returns. Return snapshots reuse the receiving-exit projection, exclude deeper block/callee bindings, and join captured maps and shared arena fields with normal method completion. Active method contexts use the existing exit-list stack for unreachable/empty/ignored checking and loop trials; noncontinuing bodies are accepted only with a reachable exit. The existing backend already restores lexical function/inline return targets when emitting yield bodies, so no closure ABI or new runtime operation is needed. Return values evaluate once, and an exit taken during value evaluation supersedes the return. Ordinary helper returns keep their own method. Top-level block returns, multiple values, escaped closures, and the existing traversal/allocation/result-join ceilings remain diagnostics. [Block-return scenarios](../features/block_return.feature) and [invoice search](../examples/invoice_search.rb) complete stage 11’s bounded literal-block contract; Symbol-to-Proc aggregation and general closure lifetimes remain separate work.

**Stage 14 namespace and class contract:** normalization retains namespace bodies, nested/absolute constant paths, constant assignments, instance/singleton method declarations, and setters. Analysis uses canonical class/module object types and per-run constant tables. Declaration bodies execute in isolated local scopes with their class/module object as receiver; constants retain lexical definition scopes, qualified declaration nesting, aliases, and ancestor lookup. Singleton methods inherit without sharing class-instance fields.

Static include/extend and, after include acceptance, prepend use ordered ancestor lists. A resolved owner includes its occurrence index, so super distinguishes duplicate included/prepended occurrences. Module methods retain lexical constants and resolve abstract host helpers only on actual receivers. Visibility declarations preserve their original return values and include native/private new access. Static attr macros feed the existing method/field analysis; invalid access remains a source diagnostic. Setter emission captures both operands once, executes the writer, and returns the original right-hand side. Native accessor argument failures use caller locations rather than synthetic method frames. Namespace and singleton calls preserve Ruby backtraces.

Runtime class/module objects reuse arena field maps; constants store shared `Value` handles. Array concatenation uses independent slot storage, and equality supports acyclic scalar/nested-array values within existing shape limits. `NilCheck` retains runtime receiver evaluation and a proven predicate outcome for branch analysis. Its emitted check stays dynamic, allowing existing function specialization to remain correct as class fields change. One-argument p supports integer/boolean/nil inspection. The unchanged registry and modular quotes execute against CRuby. Dynamic mutation, class reopening, composition hooks, per-instance extension, eigenclass body state, reassigned/computed constants, cyclic/custom array equality, and broader inspection remain outside this stage. See [namespace scenarios](../features/namespaces.feature), [composition](../features/modules.feature), [prepend](../features/prepend.feature), [visibility](../features/visibility.feature), [boundaries](../features/class_model_boundaries.feature), and [registry execution](../features/class_registry.feature).

**Stage 13 argument contract:** normalized method signatures retain named required/optional/rest/post/keyword/keyword-rest/block parameters and unevaluated defaults. Caller payloads evaluate once in order; splats snapshot slots before later mutations. Analysis binds physical inputs in callee scope, reports runtime arity/keyword/conversion errors before defaults, and evaluates only omitted defaults. Implicit rest containers retain shared elements and use the existing arena and shape ceilings. Call specialization includes argument count, splat lengths, and keyword keys so omitted defaults and different keyword layouts cannot reuse an incompatible emitted function.

Named blocks identify bounded literal call sites. `.call`, user-method/constructor forwarding, and super inline the existing analyzed block body in its original capture environment. Each receiving method has its own ordinary return boundary; forwarded break retains the original receiver boundary, and nonlocal return retains its defining method. Constructor cleanup runs before a block break result overrides `new`; ordinary initializer returns still produce the object. Missing yields/callbacks use `LocalJumpError`/`NoMethodError`. No closure escapes: returning/storing blocks, custom conversions, anonymous forwarding, Symbol-to-Proc, and forwarding into built-in iterators remain diagnostics. [Argument scenarios](../features/method_arguments.feature) and [boundary scenarios](../features/method_argument_boundaries.feature) execute the contract; [configurable quotes](../examples/configurable_quotes.rb) combine it in one application example.

**Stage 12 exception contract:** normalized protected sequences retain ordered rescue clauses, optional else, and ensure. Semantic analysis records exception types and snapshots alongside existing method/block/loop exits. Unreachable/ignored checks discard all exit records; handler states preserve mutations before errors. Ensure joins normal and pending exits in its own lexical scope, updates their state, and lets its own exit override the pending one. Built-in exception classes use a static superclass table; custom classes and dynamic rescue targets remain unsupported. Retry joins entry and retry states for at most 16 passes, with direct literal guard refinement inside that region; invalid block retries and unstable growth remain diagnostics.

Generated methods return `Outcome = Result<Value, Flow>`. Exception flow stores a shared `RubyError`; native returns/labels stay within their Rust scope, while exits crossing a protected, traced, or inlined-call closure carry a target and value until cleanup completes. Handler and ensure scopes restore the dynamic current exception, preserving bare raise and cause chains. Runtime operations check zero divisors, invalid negative array writes, and frozen string mutations before applying their effects. Error messages retain shared strings and frozen metadata. Uncaught failures print the first Ruby backtrace, source snippets from the pinned `error_highlight` library where applicable, causes, and exit status 1. No Ruby error uses a Rust panic. I/O beyond the stage 16 text contract, custom exception classes, backtrace mutation, and keyword raise arguments are outside this implemented contract. [Exception scenarios](../features/exceptions.feature) and [recoverable price quotes](../examples/recoverable_quote.rb) execute the declared boundary.

**Remaining memory-management proposal:** long-lived allocation and escaped closures need further lifetime contracts. The current arena handles object/array/hash cycles through program exit, but does not reclaim unreachable entries. String buffers contain bytes only, so their reference counts cannot form object cycles. Prototype reclamation or a tracing collector when long-lived workloads require it. `Rc<RefCell<_>>` alone would not reclaim reference cycles and can introduce borrow-check panics. No collector algorithm is chosen yet. ([Ruby: String](https://docs.ruby-lang.org/en/3.4/String.html); [Ruby: Array](https://docs.ruby-lang.org/en/3.4/Array.html); [Rust: Interior mutability](https://doc.rust-lang.org/book/ch15-05-interior-mutability.html); [Rust: Reference cycles](https://doc.rust-lang.org/book/ch15-06-reference-cycles.html))

## The first milestone tests behavior, not language size

**Stage 15 source-loading contract:** `frontend.loader` coordinates the existing reader, Prism parser, and normalizer for statically named dependencies. Unconditional file-level require_relative and restricted explicit-path require produce nested SourceLoad IR; a per-compilation realpath table prevents repeated/circular expansion. The entry file is not initially marked as required. Relative loads use the requiring file's canonical directory; explicit relative require uses compilation cwd. Parse and semantic errors retain each dependency's Ruby span, and all dependencies are checked before writing a project.

Namespace calls pass through semantic lookup before loading diagnostics. User instance/singleton methods with loader names retain priority, module helpers resolve on actual hosts, and lexical constants may shadow Kernel. Fixed built-in loading calls in unsupported contexts remain E_LOAD, including unused methods. This keeps Ruby name resolution in analysis.

Analysis keeps file-local scopes independent while sharing constants, canonical class/module values, and object state in load order. Emission reuses existing traced closures and inline local bindings. Required-file warnings execute once at the load site; successful first loads return true, repeated/in-progress loads return false. Backtraces retain the standard require/require_relative loader and `<top (required)>` frames. The source adapter captures this pinned CRuby's standard require frames with TracePoint while requiring already-loaded Prism; it executes no application code and excludes compiler-only wrappers such as Zeitwerk. SourceLoad carries that metadata into emission. Differential scenarios exercise both Bundler startup and plain CRuby startup.

The compiled project contains all dependency behavior and needs no Ruby files at runtime. Conditional/method/block/namespace-body loads, computed paths, load/autoload, arbitrary load-path or gem discovery, native extensions, and mutable loaded-feature state remain diagnostics. Custom host require wrappers need a separate contract. [Loading scenarios](../features/source_loading.feature) and [multi-file quotes](../examples/workloads/multi_file_quote.rb) execute this boundary. ([Ruby: Kernel loading](https://docs.ruby-lang.org/en/3.4/Kernel.html#method-i-require_relative))

**Stage 16 text I/O contract:** frontend GlobalRead IR represents standard stream reads; analysis resolves them and unshadowed stream/File constants into IOReference values. Existing Builtin IR carries I/O operations, validated scalar arguments, result types, and Ruby spans. User output methods and lexical constant shadows keep lookup priority. Filesystem effects occur only in the generated program; the source loader never reads application data. Standard-library file and stream operations return the existing Outcome/Flow errors, recording caller/native frames, errno classes, causes, and cleanup. Analysis records only possible I/O error classes rather than an unknown exception, preserving unrelated rescue states. Shared argument validation captures each type before later assignments and discards effects/exits after a guaranteed failure, including subsequent arguments, block expressions, and callee bodies. Unsupported dead syntax is still checked. SystemCallError/errno construction remains unsupported. All arguments are evaluated before conversion and output, retaining aliased strings. Output calls returning nil remain false loop predicates.

Linux, valid UTF-8 input, default separators/verbosity, whole-file reads/truncating writes, and standard stream gets/read/print/puts/write/flush form the declared contract. EOF differs between gets (nil) and read (empty string); counts measure bytes. Invalid bytes explicitly fail outside the input contract. Close/reopen, dynamic stream replacement, modes, offsets, encoding conversion, File.open, and custom or collection output/inspection are rejected. One-argument p uses pinned scalar inspection; Symbol values retain their compiler-generated inspection text. The committed Unicode nonprintable-range table is generated with pinned CRuby by bin/generate-inspection-table, avoiding dependence on Rust's different Unicode version. [I/O scenarios](../features/practical_io.feature) compare complete execution, including literal/runtime Unicode inspection, argument failures, interactive flush, wrong-direction errors, ENOENT/EISDIR/ENOSPC, cause chains, and standalone data reads after source removal. [Receipt export](../examples/workloads/text_report.rb) combines input, fields, file output, and error cleanup.

**Stage 17 artifact contract:** compiler generation continues through the existing per-run frontend/analysis services. Build and run share the writer/Cargo runner and select debug or release profiles; build copies an executable into a previously absent destination without executing it. Optional retention keeps emitted Rust, the copied runtime, a source map, and Cargo build artifacts even when Cargo fails. Destination checks reject occupied outputs and binary/project overlap, including aliases; exclusive creation protects the final binary from a destination created after preflight. No compilation context or incremental cache is added.

IR inspection serializes normalized or validated programs as versioned JSON node graphs, preserving identity and cycles with references and using a fresh table per dump. Backend source markers associate generated lines with the innermost Ruby IR span. Cargo JSON diagnostics map primary spans in src/main.rs to Ruby paths/lines/columns and preserve rendered Rust diagnostics; unmapped runtime/infrastructure failures retain their own locations. Maps describe unmodified emitted source, not arbitrary edits or debugger/DWARF mappings. [Artifact scenarios](../features/compiler_artifacts.feature) execute standalone debug/release binaries after Ruby source removal and independently rebuild retained projects. A component test injects a real Rust compilation failure in a loaded dependency, checks its Ruby location, and rebuilds the retained failing project.

**Planned Rubast MVP:** one file; `nil`, `true`, `false`, integers, and UTF-8 strings; locals and assignment; expression sequences; `if`/`unless`, `while`, `&&`/`||`; arithmetic and comparisons for proven integers; simple methods with positional arguments and `return`; restricted `puts`. Supporting a form means preserving its Ruby value and side-effect order. For example, `0` and the empty string are truthy; `nil || 7` returns `7`, `0 && 7` returns `7`, and an `if` branch with no selected alternative returns `nil`. Default and keyword arguments, splats, blocks, `Proc`, classes, modules, `require`, `rescue`/`ensure`, `eval`, `send`, `method_missing`, reflection, threads, `Fiber`, complex encodings, and native extensions are outside this contract. These are **Rubast scope choices**, not a list of Spinel capabilities.

| Stage | Deliverable | Acceptance criterion |
| --- | --- | --- |
| 0. Contract | Pinned CRuby/Prism, a support and diagnostics matrix, and short example corpus | Every unsupported node has a Ruby location and stable code; no silent replacement with `nil` |
| 1. End-to-end slice | `rubast run` parses one file, emits Rust, and runs the binary | Supported examples with literals, locals, `if`, `while`, and `puts` match CRuby stdout, stderr, and exit status |
| 2. Expressions and methods | Expression values, logical operations, integer arithmetic, simple methods, and `return` | Differential tests cover truthiness, evaluation order, large integers, returns, and supported-operation errors |
| 3. Controlled expansion | Choose the next semantic block from a real program corpus: mutable strings, arrays, or blocks | Define identity, memory, control flow, and differential tests before declaring support |

Differential checks should run the same `.rb` file under pinned CRuby and Rubast, comparing stdout, stderr, exit status, and error type. Normalize only named unstable details, such as an absolute path in a message. Retain the source example, emitted Rust, and diagnostics so parser, analysis, code-generation, and runtime failures remain distinguishable. Spinel uses CRuby comparisons and classifies mismatches; `ruby/spec` offers a practical behavior corpus, not a formal language standard. Report two metrics separately: the share of declared-support tests and the pass rate among them. Use TDD: a Cucumber scenario defines observable behavior before implementation, RSpec checks individual passes and container wiring, and implementation makes the scenario pass. ([Spinel: Contributing](https://github.com/matz/spinel/blob/master/README.md#contributing); [ruby/spec](https://github.com/ruby/spec))

## Let the first program corpus guide open decisions

The largest unknown is **which Ruby programs Rubast is meant to compile**. Teaching examples, porting a particular application, and general-purpose compilation suggest different priorities. CRuby and Prism versions are pinned for the current slice. The integer overflow policy and permitted core methods must be defined as the supported subset expands. A corpus of real examples will show whether general dispatch, string mutation, arrays, or blocks should come next. Memory management, serialized IR, incremental builds, and type optimization should follow that evidence.

## Conclusion

Rubast should grow as a **compiler with a published semantic contract**. Every new Ruby feature needs a defined value, control flow, error behavior, data representation, and comparison with CRuby. This gives the project a path toward broader compatibility and Rust specialization without hiding early semantic differences.
